## Objective

**SG4 — Publish HomeIQ's first domain agents to AgentForge (VAL-009, VAL-010, VAL-024).**

This is the architectural payload. HomeIQ currently publishes only
`homeiq-service-auditor` and `homeiq-audit-aggregator` — no home-automation
intelligence at all, while the platform runs 178 agents. Other consumer projects
already carry their own domain experts (`web-store-wstore-expert-*`,
`hearth-goods-hearth-expert-*`); HomeIQ has none. Fix that.

- Consult **`expert-architecture`** via `invoke_task` on the decomposition before
  writing the agents. Record its advice and your disposition.
- Author as flat `.md` under `agentforge/projects/homeiq/agents/`, minimally:
  - `homeiq-ha-automation-author` — `role: task`. Input: the SG1 inventory + the
    behavioral requirement. Output: HA automation YAML conforming to a declared schema.
  - `homeiq-automation-judge` — `role: judge`. Scores YAML for correctness, safety
    (nothing that could strand a person in the dark), extensibility, and HA-schema
    validity. Returns structured findings.
- Workflow `agentforge/projects/homeiq/workflows/homeiq-automation-author.yaml`:
  2-node DAG `author → judge`.
- **AF authoring gotchas — verified against `backend/workflows/models.py`, respect
  them or the run fails silently:** node kind is `kind: task`, never `kind: agent`
  (rejected, `extra="forbid"`). Input refs are `$inventory`, **never `{{inventory}}`**
  — a `{{…}}` placeholder passes through *literally* and the agent sees raw braces,
  and `spec_version: 2` strictness will not catch it because it only validates refs
  starting with `$`. Terminal run state is `complete`, never `success`. Poll
  `GET /workflows/runs/{id}` → `run.state` (top-level `state` only exists on
  `/outputs`). **`output_schema` is enforced on the workflow node, not on the agent's
  frontmatter** — declare it on the node with `output_repair_retries: 2`.
- Publish with `scripts/af.sh publish`. **Agents before workflows** — a workflow
  referencing an unpublished agent returns 422. First publish returns 201 and
  auto-activates; a republish with an unchanged hash returns 200 and does *not*
  activate, so pass `--activate` when you need it.
- **Git is the authoring source of truth**; AF's version store is the runtime store.
  Commit the agent/workflow files (VAL-024). If you ever edit inside AF, export back
  with `af_export.py` or you have created drift.
- proof: file paths, publish responses, `GET /projects/homeiq/agents` showing them
  active, and the expert consultation record.

**SG5 — AgentForge authors the automation; HomeIQ checks it (VAL-011…VAL-016).**
- Run the AF workflow with the SG1 inventory as a **declared workflow input**. Note
  `invoke_task`'s `context` parameter is for Goal overrides only — `context.files`
  never reaches the agent. Content goes in the prompt or in declared inputs.
- Confirm the run actually resolved its inputs — a completed run is not proof the
  refs bound. Paste the run's resolved input or the agent's echo of it.
- The judge's findings are addressed or explicitly rejected with a reason. Do not
  quietly ignore them.
- **Fusion mechanism** (researched 2026-08-11; re-verify per Research above):
  - Combine sensors with a **Binary sensor group helper**, not an inline list: the
    group is `on` when *any* member is on and `off` only when *all* are off — exactly
    the OR-entry / all-clear-exit semantics, for free. Set `device_class` to
    `motion`/`occupancy`.
  - Prefer targeting the **`role:presence` label or the group** so adding a sensor
    later needs no automation rewrite. VAL-015 is satisfied by that extensibility, not
    by a long frozen list. If the current HA release cannot target labels in the
    trigger position, use the group and record why.
  - **Entry:** group → `on` ⇒ `light.office` on. **Exit:** `for: "00:05:00"` on the
    group being `off`; a single still-occupied sensor holds the lights on and the
    timer restarts on re-trigger.
  - **PIR blind spot** (real, not hypothetical): passive-infrared reports no-motion
    for a person sitting still, so lights driven off raw motion die on a stationary
    occupant. The `for:`-on-all-clear shape is the mitigation. If an adopted sensor is
    true mmWave presence, record that — it needs less margin.
  - **Manual override:** if a human turns `light.office` off while presence is still
    detected, do not immediately re-trigger. Choose `mode: restart` or a suppression
    window and state which and why.
  - **Modern HA syntax** — 2026.7.4 uses plural `triggers:`/`conditions:`/`actions:`.
- Gate: `POST :8016/lint` → 0 errors (15 rules); `POST :8037/api/v1/validation/validate`
  with `validate_entities: true`, `validate_services: true` → pass.
- proof: AF run id + terminal state + output, judge findings + dispositions, both gate
  responses.

one live system. Fanning them out is the documented worst fit.

## Loop

- **State:** `tapps_memory` recall (wayfind + prior attempts) → VAL coverage → last
  handoff → live HA state → AF publish state.
- **Decide:** lowest-numbered sub-goal whose VALs are not all green.
- **Execute:** on the committed mechanism + tier.
- **Verify (independent):** fresh-context verifier (`general-purpose`, `opus`,
  `xhigh` in a Workflow) prompted to **refute** the proof by re-running the check
  itself. Default to "not done" on doubt. The verifier **reports gaps, does not fix**.
- **On fail:** structured handoff → narrow fix sub-goal → re-execute → re-verify.
  **≤3 rounds per sub-goal**, then escalate once, then stop with a diagnosis. Never
  weaken a VAL to go green.
- **Record:** completed · undone · commands+exit codes · issues · expert advice and
  disposition · failure-and-why → `tapps_memory`.
- **Context hygiene:** the inventory artifact is large — grep it, never re-Read whole.
- **Repeat or stop:** until Done-when. Caps: **12 iterations** AND **~400k tokens**.

## Guardrails

- Termination: Done-when; caps 12 iterations AND ~400k tokens.
- **Caps must not fire on correct behavior:** `presence: proxy` with all VALs green is
  a **pass**. A service returning zero records in SG1 is a **finding**. HA starting
  with zero automations is expected.
- **Intelligence belongs in AgentForge.** Do not add LLM-calling logic to a HomeIQ
  container; that is the direction TAP-5300/TAP-5302 retire. HomeIQ collects, calls,
  deploys, tests. AF reasons.
- **Never write HA YAML, a template function, or a service call from memory** — look
  it up first. A hallucinated schema that lints clean but targets a removed key is the
  likeliest cause of a failed run.
- Every subagent dispatch names `agentType` + `model` (+ `effort` in a Workflow);
  read-only steps use `Explore` so the tool boundary enforces it. After any
  `general-purpose` fan-out run `git status` — it holds Edit/Write regardless of the
  prompt, and has silently modified a file in this repo before.
- No fan-out of coupled writes — SG2/SG3/SG6 serial.
- **Never print the HA token or the `afp_*` key.** Do not read `.env` / `.env.*`.
- `--env-file .env` on every single-service compose command.
- **No green-by-suppression:** do not shorten the 5-minute delay, relax a linter rule,
  or drop an assertion to pass.
- Scope: HomeIQ repo + AF project `homeiq` + the live HA. **No writes to AgentForge
  platform code or TappsMCP** — defects there become Linear issues in *their* projects
  via the `linear-issue` skill.
- Discipline: root cause not workarounds; right-sized; durable; no scope creep.

## Failure handling

- On failed verify: diagnose (real error + live state + brain recall) → hypothesis →
  fix → retry with *something changed*. Never re-run the same call on the same error.
- ≤3 distinct strategies per sub-goal, then escalate once, then stop with a diagnosis.
- First verify failure is expected. Scope a narrow fix; do not reopen the whole
  automation or rewrite the contract.
