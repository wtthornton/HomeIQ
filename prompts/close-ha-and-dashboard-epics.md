## Loop

- **State:** read Linear for the two epics (via `linear-read`); `git log --oneline -5`;
  contract script current score; brain recall of prior failures.
- **Decide:** lowest-numbered sub-goal not yet verified-done. One at a time.
- **Execute:** on the committed mechanism above. Code edits sequential, in-session.
  After each `src/` Python edit run `tapps_quick_check`; at each story gate run
  `tapps_validate_changed(file_paths=...)` with explicit paths.
- **Verify (independent):** spawn a **fresh-context verifier subagent (frontier)** told to
  **refute** the sub-goal's proof — it re-runs the deterministic check itself and defaults
  to "not done" on any doubt. **Its verdict advances the loop, not the executor's claim.**
- **On fail:** diagnose — read the actual error, inspect state, recall prior failures —
  then hypothesis → fix → retry *with something changed*. ≤3 distinct strategies per
  sub-goal, then escalate once (stronger model / different approach), then stop with a
  concise diagnosis. **Never re-run the same action on the same error.**
- **Record:** `uv run tapps-mcp memory save --key <slug> --tier pattern --value "<outcome incl. what failed and why>"`.
- **Context hygiene:** prune stale reads each iteration; prefer targeted `grep` over a full
  re-`Read`; carry a compact state summary forward, not raw transcripts. Delegate any
  noisy multi-file reading to a subagent and keep only its summary.
- **Print every iteration:**
  `SCORE: contract <pass>/36 · pytest <fail> failures · stories done <n>/12 · iteration <i>/40`
- **Repeat or stop:** until Done-when holds; caps **40 iterations** AND **1.2M output tokens**.

## Guardrails

- **Termination:** the Done-when artifact set; caps 40 iterations AND 1.2M output tokens.
- **Independent verification** — a verifier that did not do the work, against ground truth.
- **🔴 DO NOT MUTATE THE LIVE HOME ASSISTANT.** The user's standing instruction is
  "do not set anything up." Read-only calls against `192.168.1.80` are permitted and expected
  (`audit` mode). Any `apply` against the live HA — backups, add-ons, HACS, registries — is an
  **Autonomy hard-stop** requiring explicit authorization. Develop and test against
  `ha-simulator` and fixtures. This epic delivers a *working agent*, not a *configured home*.
- **Caps must not fire on correct behavior:** an `audit` run that finds every recipe
  `NEEDS_APPLY` is a **correct, passing** result — the home is genuinely unconfigured. Do not
  treat a non-empty needs-apply list as failure.
- **No fan-out of coupled coding** — nginx, the SPA, and `libs/homeiq-ha` are edited
  sequentially in-session. Fan-out is for research and verification only.
- **Context hygiene** — targeted grep over full re-Read; summaries over transcripts.
- **Scope:** `/home/wtthornton/code/HomeIQ` only. Linear team `TappsCodingAgents`, project
  `HomeIQ`. Cross-project writes are forbidden (`agent-scope.md`).
- **Memory:** recall at start, record at every checkpoint including failures.
- **Harness compatibility:** Linear writes via `linear-issue` (30-min sentinel), multi-reads via
  `linear-read` (cache gate), `tapps_session_start` before any `tapps_*` tool. Per-edit quality
  nudge **adopted for `src/` Python**, **overridden to story-gate batching** for tests and docs.
- **Discipline:** root-cause not workarounds; **no green-by-suppression** — never skip, disable,
  or weaken a test or checker to go green; right-sized; durable over expedient; match repo
  conventions; no silent scope creep. If the correct fix is out of scope, stop and say so.
- **Secrets:** `.env` is gitignored and stays that way. Never commit a key. Note
  `backup/config/info` returns the HA backup encryption key in plaintext — never log it.

## Autonomy

- Act on every reversible, in-scope step. No "should I proceed?" checkpoints.
- Irreversible/outward → produce the reversible precursor (branch + draft PR, staged diff)
  and keep going; the human reviews async. **A draft PR is not a stop.**
- **Hard-stop once (batched, with a recommendation) only for:** any write to the live Home
  Assistant · merge to `master` · force-push · deleting un-recreatable data · a genuinely
  ambiguous decision where a wrong guess is expensive (the evaluations datastore choice and
  the two unmatched dashboard panels are candidates — but **decide and proceed** if the repo
  or its tests imply an answer).

## Failure handling

Diagnose, don't repeat. Read the real error → inspect state → recall prior failures →
form a specific hypothesis → change something → retry. ≤3 distinct strategies per sub-goal,
then one escalation, then stop with a concise diagnosis naming what you tried and why each failed.
